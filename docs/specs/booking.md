# Спецификация: сервис записи на звонки

> Статус: согласовано 2026-11-20. Собран из решений карты [«Карта: сервис записи на звонки — спецификация и план работ»](https://github.com/Aleksandra-korza/frontend-project-386/issues/1) и `docs/requirements.md`. Реализация — по тикетам плана, после подтверждения.
> Термины — `GLOSSARY.md`. Архитектурные решения — `docs/adr/0001`…`0005`. Главная страница — `docs/specs/home-page.md`.

## 1. Роли и сценарии

| Роль         | Описание                                                                                                                                    | Источник                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| **Владелец** | Один неявный заранее заданный профиль; без регистрации и авторизации; работает в «Разделе владельца» `/admin`; сущности и ресурса в API нет | ROLE-01, D-05, тикет #2 |
| **Гость**    | Записывается на встречу без регистрации                                                                                                     | ROLE-02                 |

Сценарии — UC-01…UC-05 (`docs/requirements.md` §3) без изменений:

- **UC-01** владелец создаёт тип встречи в `/admin` (§6.2);
- **UC-02** владелец видит все предстоящие бронирования одним списком независимо от типа (§6.2);
- **UC-03** гость: главная → каталог → тип → день → слот → подтверждение → успех (§6.1);
- **UC-04** конфликт при подтверждении (§4, §6.1);
- **UC-05** повторное бронирование, тот же email допустим (BR-22).

## 2. Сущности

**Тип встречи** (тикеты #2, #3; BR-06…BR-08):

| Поле              | Тип     | Правила                                                                                                                                  |
| ----------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `id`              | string  | slug, задаёт владелец, **уникален и неизменяем**; 3–40 символов: строчная латиница, цифры, одиночные дефисы между частями (`intro-call`) |
| `title`           | string  | обязателен; пробелы по краям обрезаются; 1–80 символов после обрезки                                                                     |
| `description`     | string? | необязателен; обрезка пробелов; ≤ 500 символов; пустая строка = отсутствует                                                              |
| `durationMinutes` | integer | 15–480 включительно, кратно 15 (BR-07)                                                                                                   |

Тип можно только **создать** (D-15): редактирования и удаления нет. Каталог — в порядке создания, старые первыми.

**Бронирование** (тикеты #2, #6; BR-20…BR-23):

| Поле            | Тип      | Правила                                                                 |
| --------------- | -------- | ----------------------------------------------------------------------- |
| `id`            | string   | генерирует сервер                                                       |
| `meetingTypeId` | string   | существующий тип                                                        |
| `startsAt`      | datetime | начало допустимого слота (§3)                                           |
| `endsAt`        | datetime | вычисляет сервер: `startsAt + durationMinutes`; хранится в бронировании |
| `guestName`     | string   | обязательно; обрезка пробелов; 1–100 символов после обрезки (BR-21)     |
| `guestEmail`    | string   | обязательно; ≤ 254 символов; формат email                               |
| `createdAt`     | datetime | момент создания (FR-22)                                                 |

Интервал `startsAt`/`endsAt` хранится в бронировании и не зависит от последующих изменений типа. Бронирование нельзя отменить или перенести (D-10).

**Слот** — вычисляемое значение, не хранится: интервал встречи выбранного типа, начинающийся в точке сетки, со статусом «свободен / занят». Хранятся только типы встреч и бронирования — в памяти процесса (D-06).

**Время в API** — ISO 8601 со смещением `Europe/Warsaw` (`2026-11-21T10:00:00+01:00`); день — `YYYY-MM-DD` (тикет #2).

## 3. Доступность времени

Источник истины — **сервер** (ADR-0004, тикет #5); клиент только отображает.

| Правило                        | Значение                                                                                                                                         | Источник        |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------- |
| Часовой пояс                   | `Europe/Warsaw` для «сегодня», окна, сетки и отображения                                                                                         | BR-03           |
| Окно бронирования              | 14 календарных дней, начиная с завтрашнего (N+1 … N+14), сдвигается со временем                                                                  | BR-01, BR-02    |
| Рабочие дни и часы             | все дни недели; 09:00–18:00; встреча целиком внутри                                                                                              | BR-04, BR-05    |
| Длительность слота             | равна `durationMinutes` типа                                                                                                                     | BR-09           |
| Шаг начала                     | 30 минут от 09:00: точки 09:00…17:30 (18 точек)                                                                                                  | BR-10           |
| Последнее начало               | 18:00 − длительность, вниз до шага (15 мин → 18 стартов, 60 мин → 17, 480 мин → 3)                                                               | BR-11           |
| Свободный слот                 | не пересекается ни с одним бронированием любого типа                                                                                             | BR-12, BR-16    |
| Счётчик                        | число свободных слотов дня для выбранного типа; считает клиент по ответу API                                                                     | BR-13, тикет #5 |
| Полностью занятый день         | недоступен для выбора в календаре; его слоты остаются в ответе API                                                                               | тикет #5        |
| Переход на летнее/зимнее время | сетка — в местном времени Варшавы; сравнение интервалов по абсолютным моментам; в дни перехода (2026-03-29, 2026-10-25) меняется только смещение | ADR-0004        |
| Текущее время                  | источник времени подставляется в сервис (тесты задают фиксированный момент)                                                                      | ADR-0004        |

Даты и время в коде — `Temporal` через `temporal-polyfill` на backend и frontend (ADR-0004).

## 4. Пересечения и одновременные запросы

- Интервалы `[a1, b1)` и `[a2, b2)` конфликтуют, если `a1 < b2 && a2 < b1` (BR-14, BR-15). **Примыкание допустимо** (BR-17): бронирование 10:00–11:00 запрещает 10:30–11:00 и 10:00–10:30, но допускает начало в 11:00.
- Запрет действует для любых типов: календарь владельца один (BR-16).
- **Порядок проверок** при создании бронирования (ADR-0003): существование типа — неизвестный `meetingTypeId` даёт `404 MEETING_TYPE_NOT_FOUND` → данные гостя (`400`) → `startsAt` — допустимый слот: точка сетки в окне и в рабочих часах, сравнение абсолютных моментов; строка без смещения — `INVALID_FORMAT`, недопустимый слот — `INVALID_SLOT` (`400`) → пересечения (`409 SLOT_TAKEN`).
- **Атомарность** (BR-18, ADR-0003): поиск пересечений и вставка — одна синхронная операция в одном процессе Node.js, без `await` между ними; линейный перебор бронирований.
- Конфликт не раскрывает данные чужого бронирования. Механизма идемпотентности нет: повторный запрос на занятое время — конфликт; двойная отправка блокируется в интерфейсе.

## 5. API-контракт (TypeSpec)

Контракт описывается в `api/main.tsp`; `mise run codegen` генерирует `api/generated/openapi.json` (OpenAPI 3.0), SDK frontend и типы backend; CI проверяет актуальность сгенерированного кода. Backend — ручные маршруты Fastify со схемами из `openapi.json` и контрактные тесты (ADR-0005).

| operationId                  | Метод и путь                               | Тело запроса                                         | Успешный ответ                                                                                                          |
| ---------------------------- | ------------------------------------------ | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `getHealth`                  | `GET /api/health`                          | —                                                    | `200` `{ status: "ok" }` (есть)                                                                                         |
| `listMeetingTypes`           | `GET /api/meeting-types`                   | —                                                    | `200` `MeetingType[]` в порядке создания                                                                                |
| `createMeetingType`          | `POST /api/meeting-types`                  | `{ id, title, description?, durationMinutes }`       | `201` `MeetingType`                                                                                                     |
| `getMeetingType`             | `GET /api/meeting-types/{id}`              | —                                                    | `200` `MeetingType`                                                                                                     |
| `getMeetingTypeAvailability` | `GET /api/meeting-types/{id}/availability` | —                                                    | `200` `{ timeZone: "Europe/Warsaw", window: { from, to }, days: [{ date, slots: [{ startsAt, endsAt, available }] }] }` |
| `createBooking`              | `POST /api/bookings`                       | `{ meetingTypeId, startsAt, guestName, guestEmail }` | `201` `Booking`                                                                                                         |
| `listUpcomingBookings`       | `GET /api/bookings`                        | —                                                    | `200` `[Booking + meetingTypeTitle]`, только будущие (BR-24), по возрастанию `startsAt`                                 |

### Ошибки

Единое тело: `{ code, message, fieldErrors?: [{ field, code }] }`; модель ошибки поля описывается в TypeSpec явно. `message` — технический текст на английском; тексты для пользователя интерфейс выбирает по кодам.

| HTTP  | `code`                   | Когда                                                                                      |
| ----- | ------------------------ | ------------------------------------------------------------------------------------------ |
| `400` | `VALIDATION_ERROR`       | неверный формат, обязательные поля, ограничения длины и диапазона, недопустимый `startsAt` |
| `404` | `MEETING_TYPE_NOT_FOUND` | неизвестный `id` типа (`getMeetingType`, доступность, `createBooking`)                     |
| `409` | `MEETING_TYPE_ID_TAKEN`  | тип с таким `id` уже существует                                                            |
| `409` | `SLOT_TAKEN`             | выбранное время пересекается с существующим бронированием                                  |

### Ошибки полей

`fieldErrors` возвращается только с `400 VALIDATION_ERROR` и содержит **все** поля с ошибками сразу, по одной записи на поле. `field` — имя поля запроса. Длины считаются после обрезки пробелов по краям там, где она предусмотрена (`title`, `description`, `guestName`).

| `code`           | Когда применяется                                                                                                                                                                                                                                                  | Поля                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `REQUIRED`       | поле отсутствует или равно `null`; для `title` и `guestName` — также пустая строка после обрезки пробелов                                                                                                                                                          | `id`, `title`, `durationMinutes`, `meetingTypeId`, `startsAt`, `guestName`, `guestEmail` |
| `TOO_LONG`       | длина превышает максимум: `title` > 80, `description` > 500, `guestName` > 100, `guestEmail` > 254                                                                                                                                                                 | `title`, `description`, `guestName`, `guestEmail`                                        |
| `INVALID_FORMAT` | значение не того типа или не того формата: `id` не соответствует slug-формату или длине 3–40; `guestEmail` — не email; `startsAt` — не дата-время ISO 8601 со смещением (в том числе без смещения); `durationMinutes` — не целое число; строковое поле — не строка | `id`, `title`, `description`, `durationMinutes`, `guestName`, `guestEmail`, `startsAt`   |
| `OUT_OF_RANGE`   | `durationMinutes` — целое число, но меньше 15, больше 480 или не кратно 15                                                                                                                                                                                         | `durationMinutes`                                                                        |
| `INVALID_SLOT`   | `startsAt` корректного формата, но не совпадает с началом допустимого слота этого типа: не точка сетки 30 минут, встреча выходит за 09:00–18:00 или день вне окна бронирования (в том числе прошлое и сегодня)                                                     | `startsAt`                                                                               |

`description` никогда не получает `REQUIRED`. Занятое время — не ошибка поля: на корректный слот, пересекающийся с бронированием, сервер отвечает `409 SLOT_TAKEN`. Неизвестный, но непустой `meetingTypeId` в `createBooking` — не ошибка поля, а `404 MEETING_TYPE_NOT_FOUND` (проверяется первым, ADR-0003).

## 6. Интерфейс

### 6.1. Гость (тикет #8; ADR-0001, ADR-0002)

| Адрес                              | Экран                                                                                                                                                                                                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/book`                            | Каталог: карточка-ссылка на тип — название, описание (если есть), длительность («30 мин», «1 ч 30 мин»)                                                                                                                                                                        |
| `/book/:typeId?date=YYYY-MM-DD`    | Выбор дня и времени: собственный календарь Пн–Вс (Tailwind + Temporal) со счётчиком свободных слотов в днях окна; стрелки месяцев только в пределах окна; список всех слотов дня (занятые — неактивны); информационная панель; «Назад» → каталог, «Продолжить» → подтверждение |
| `/book/:typeId/confirm?startsAt=…` | Подтверждение: сводка, поля «Имя» и «Email» (на клиенте только `required` и `type="email"`), «Изменить» → выбор дня, «Подтвердить запись» (блокируется на время отправки); после успеха — экран успеха на том же адресе                                                        |

- День при входе не выбран; информационная панель: тип, длительность, выбранные день и время, число свободных слотов дня, часовой пояс из ответа API (FR-08).
- Данные — loaders React Router; индикатор загрузки; `ErrorBoundary` маршрутов; revalidation после бронирования и конфликта.
- При `SLOT_TAKEN` и при ошибке поля `startsAt` с кодом `INVALID_SLOT` — возврат на выбор того же дня с повторно загруженной доступностью и соответствующим сообщением (§6.3); имя и email не сохраняются.

### 6.2. Владелец — «Раздел владельца» `/admin` (тикет #9)

- Одна страница: сначала «Предстоящие бронирования», затем «Типы встреч». Общая шапка без ссылки на `/admin` (FR-21); раздел не защищён (SEC-01).
- **Бронирования:** по `startsAt` по возрастанию, сгруппированы по дням; в записи — время («10:00–11:00»), тип встречи, имя и email гостя, «Создано: дд.мм.гггг, чч:мм»; часовой пояс — в заголовке секции; без автообновления.
- **Типы встреч:** список в порядке создания (`id`, название, длительность, описание) и форма создания: поле «Идентификатор (id)» с подсказкой формата, название, описание, длительность — выпадающий список 15…480 мин с подписями в часах и минутах. Отправка — action React Router; после успеха — revalidation, очистка формы, сообщение; ошибки у полей, `MEETING_TYPE_ID_TAKEN` — у поля `id`; кнопка блокируется на время отправки.

## 7. Тестирование (тикет #10)

| Уровень                        | Что проверяет                                                                                                                                                                                | Инструмент и место                                         |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Модульные                      | BR-01…BR-17, BR-20…BR-21 с фиксированными часами: окно, сетка, последнее начало, пересечение и примыкание, проверка `startsAt`, поля; DST 2026-03-29 и 2026-10-25; длительности 15 и 480 мин | Vitest, `apps/backend`                                     |

| Конкурентность (NFR-02)        | 10 одинаковых и пересекающиеся запросы разных типов через `Promise.all`: ровно одно успешное, пересечений нет                                                                                | настоящий HTTP                                             |
| Контрактные                    | ответы соответствуют `openapi.json`                                                                                                                                                          | Vitest + ajv (`inject()`), есть                            |
| Страницы frontend              | каталог, выбор дня и слота, счётчик, подтверждение и ошибки полей, `SLOT_TAKEN` с обновлением, создание типа и список бронирований в `/admin`                                                | Testing Library + happy-dom, подмена только `fetch`        |
| Браузерные (настоящие серверы) | 1) основной путь: тип в `/admin` → бронирование гостем → бронирование в `/admin`; 2) конфликт: слот занят через API во время заполнения формы                                                | Playwright, пакет `e2e/`, уникальные типы, без seed-данных |
| Проверка с нарушенным правилом | временно нарушить правило пересечения → `mise run check` падает на тестах пересечения и конкурентности → восстановить; вывод приложить к тикету                                              | разово, в тикете реализации бронирования                   |

Команды: `mise run check` — всё, кроме браузерных (pre-push и CI); `mise run e2e` — Playwright (в CI отдельная job в `check.yml` с Chromium и загрузкой отчёта). Порог покрытия не вводится.

## 8. Релизы (тикет #13)

release-please подключается отдельным тикетом сразу после первой сквозной функции: одна версия репозитория (manifest, пакет `.`, тип `node`, начальная версия `0.1.0`), релизы из `main`, отдельный workflow `release-please.yml`, action по полному SHA, без PAT, release PR сливается squash-ом с заголовком по Conventional Commits.
