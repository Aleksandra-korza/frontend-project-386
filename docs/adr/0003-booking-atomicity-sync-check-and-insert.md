# Атомарность бронирования за счёт синхронной проверки и вставки

Бронирования хранятся в памяти одного процесса Node.js (D-06), а запрет пересечений должен соблюдаться и при одновременных запросах (BR-14…BR-18). Поиск пересечений и вставка бронирования выполняются **одной синхронной операцией** хранилища: между проверкой и вставкой нет `await`, колбэков, таймеров или иной передачи управления event loop, поэтому обработка другого запроса не может вклиниться между ними. Пересечения ищутся линейным перебором всех бронирований — при одном владельце, окне в 14 дней и не более 18 встреч в день этого достаточно.

Решение принято в тикете карты «Атомарность бронирования и конфликты при параллельных запросах» (GitHub issue #6).

## Порядок проверок при создании бронирования

1. Тип встречи существует — иначе «не найден».
2. Данные гостя корректны (BR-20, BR-21) — иначе ошибка валидации.
3. `startsAt` — допустимый слот этого типа: точка сетки шага 30 минут, внутри окна бронирования, встреча целиком в рабочих часах (BR-01…BR-11) — иначе ошибка валидации. `endsAt` вычисляет сервер: `startsAt + durationMinutes`.
4. Интервал `[startsAt, endsAt)` не пересекается ни с одним бронированием любого типа (`начало1 < конец2 && начало2 < конец1`; примыкание допустимо) — иначе конфликт. Шаг 4 и вставка — одна синхронная операция.

Конфликт возникает только для корректного запроса на занятое время, поэтому интерфейс отличает «время занято» (FR-19) от неверного запроса (TC-07). Конкретные HTTP-коды — в тикете «API-контракт на TypeSpec и модель ошибок».

## Конфликт и повторные запросы

- Ответ о конфликте не раскрывает сведений о другом бронировании (имя, email, тип встречи): только сообщение «выбранное время уже занято». Данные гостей видит лишь владелец в `/admin`.
- Отдельного механизма идемпотентности (ключа запроса) нет: повторный запрос на уже занятое время, в том числе двойное нажатие «Подтвердить», получает конфликт. Защита от двойной отправки — на уровне интерфейса.

## Тестовые инварианты (NFR-02)

- N одновременных запросов (`Promise.all`) на одно и то же время одного типа: ровно одно бронирование создано, остальные получают конфликт.
- Одновременные запросы на пересекающиеся интервалы разных типов (например, 10:00 на 60 минут и 10:30 на 30 минут): ровно одно успешное бронирование, остальные — конфликт.
- В обоих случаях после запросов в хранилище нет пересекающихся интервалов.

## Considered Options

- **Очередь или мьютекс на календарь владельца** — нужны, только если между проверкой и вставкой появится асинхронность; сейчас добавляют сложность без пользы.
- **Дерево интервалов или отсортированный индекс** — преждевременная оптимизация при текущем объёме данных.

## Consequences

- Атомарность держится только на синхронности одного event loop. Любой `await` внутри проверки и вставки незаметно сломает BR-18 — поэтому правило зафиксировано здесь и проверяется тестом на одновременные запросы.
- **Trade-off:** при переходе на базу данных или на несколько процессов/экземпляров синхронность одного event loop больше не гарантирует атомарность. Потребуется транзакция с подходящим уровнем изоляции или ограничение уникальности/исключения на стороне БД, либо внешняя блокировка; это решение тогда нужно пересмотреть.
