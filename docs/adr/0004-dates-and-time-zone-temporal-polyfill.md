# Даты и часовой пояс — Temporal через temporal-polyfill

Все даты, время и окно бронирования считаются в `Europe/Warsaw` (BR-03), а API обменивается временем в ISO 8601 со смещением и днями в `YYYY-MM-DD`. Для этого backend и frontend используют один подход — `Temporal` через пакет `temporal-polyfill` (`import { Temporal } from 'temporal-polyfill'`): при наличии нативного `Temporal` пакет использует его, иначе — полифил. В Node.js 24 `Temporal` доступен только за экспериментальным флагом, поэтому без полифила не обойтись.

Решение принято в тикете карты «Формирование доступного времени и вычисление слотов» (GitHub issue #5) на основе исследования «Даты и часовой пояс Europe/Warsaw: библиотека для Node 24 и браузера» (issue #4, ветка `research/date-timezone`).

## Почему не date-fns + @date-fns/tz

`date-fns` + `@date-fns/tz` (`TZDate`) дают те же сетки и строки и легче (≈8,6 KB против ≈19 KB gzip во frontend), но:

- `Temporal` даёт **явные типы** для местной даты (`PlainDate`), момента (`Instant`) и времени в зоне (`ZonedDateTime`), поэтому смешать местное время и момент сложнее;
- поведение для неоднозначного или несуществующего местного времени при переходе на летнее/зимнее время **задаётся явно**;
- строка времени **без смещения отклоняется**, тогда как `parseISO` молча принимает её как местное время — для API это источник ошибок;
- один и тот же стандартный API на backend и frontend, без промежуточного слоя.

## Правила вычисления доступного времени

1. **Источник истины — сервер.** Он вычисляет слоты и их занятость; клиент только отображает результат и не строит собственную сетку (BR-19).
2. **Ответ API — всё окно сразу:** границы окна бронирования (14 дней, начиная с завтрашнего, BR-01) и для каждого дня все слоты выбранного типа со статусом «свободен / занят». Это не больше 14 × 18 = 252 слотов.
3. **Счётчик** свободных слотов дня (FR-11, BR-13) клиент вычисляет по полученному списку; отдельного поля в API нет.
4. **Полностью занятый день** недоступен для выбора в календаре; его занятые слоты остаются в ответе API.
5. **Текущее время.** «Сегодня» и окно сервер определяет от текущего момента в `Europe/Warsaw`; источник времени подставляется в сервис (параметр часов), чтобы тесты задавали фиксированный момент.
6. **Переходы на летнее/зимнее время.** Сетка строится в местном времени Варшавы: точки начала 09:00–17:30 с шагом 30 минут — 18 точек в день; для конкретного типа последнее начало ограничено BR-11. Интервалы сравниваются как абсолютные моменты (`Instant`). Переходы происходят ночью, вне рабочих часов, поэтому в такие дни местная сетка не меняется — меняется только смещение в ISO-строках (`+01:00` / `+02:00`). Тесты обязательно включают дни перехода **2026-03-29** и **2026-10-25**.
7. **Проверка `startsAt` при бронировании** (шаг 3 в ADR-0003) использует **ту же функцию** построения сетки, что и выдача доступности: `startsAt` допустим, если его абсолютный момент совпадает с началом одного из слотов этого типа в окне. Строка без смещения отклоняется как ошибка валидации; строка с другим смещением (например, `Z`) принимается, если обозначает тот же момент.

## Consequences

- Во frontend добавляется ≈19 KB gzip полифила; при нативном `Temporal` в браузере он не используется.
- Логика сетки, окна и проверки `startsAt` живёт в одной функции на сервере; клиент зависит от формата ответа, а не от правил.
- Тесты не зависят от реальной даты благодаря подставляемым часам.
- При переходе на Node.js 26, где `Temporal` включён по умолчанию, полифил на backend можно убрать — после проверки совместимости API нативной реализации с используемым кодом. Во frontend полифил остаётся, пока целевые браузеры (Safari) не поддерживают `Temporal` в стабильных версиях.
- Если `Temporal` или полифил окажутся непригодны, запасной вариант — `date-fns` + `@date-fns/tz` с обязательной ручной проверкой смещения во входящих строках.
