# Проект: Календарь звонков

## 1. Цель проекта

В этом проекте мы проходим полный цикл разработки небольшого веб-приложения, где основным исполнителем выступает ИИ-агент.

Сначала создаём каркас приложения и настраиваем агентную среду, затем проектируем функциональность через спецификацию, реализуем её по тикетам и публикуем готовый сервис.

Работа проходит по единому циклу:

1. Обсуждаем задачу.
2. Фиксируем требования и спецификацию.
3. Разбиваем работу на небольшие тикеты.
4. Реализуем функциональность с помощью ИИ-агентов.
5. Проверяем результат тестами.
6. Публикуем приложение.

Ключевой принцип: разработку выполняем с помощью ИИ-агентов. Разработчик формулирует задачи, контролирует процесс, проверяет результат и принимает окончательные решения.

Проект можно выполнить на любом технологическом стеке. Обязательное условие: приложение должно собираться в Docker-образ и запускаться в контейнере.

## 2. Описание приложения

«Календарь звонков» — упрощённый сервис бронирования времени для встреч по мотивам Cal.com.

Cal.com — сервис, в котором владелец публикует доступное время, а другие пользователи выбирают свободный интервал и бронируют встречу.

Наше приложение реализует аналогичный основной сценарий, но без сложных возможностей полноценного сервиса.

В приложении предусмотрены две роли:

- Владелец календаря — один заранее заданный пользователь.
- Гость — человек, который хочет записаться на встречу.

Авторизация, личные кабинеты, интеграции с внешними календарями и уведомления не входят в обязательный объём проекта.

## 3. Функциональность

### 3.1. Возможности владельца

В приложении предусмотрен один владелец календаря.

Он должен иметь возможность:

- Создавать типы встреч.
- Указывать название каждого типа встречи.
- Добавлять описание.
- Указывать длительность встречи.
- Просматривать список предстоящих записей всех типов встреч.

Отдельная система регистрации и авторизации владельца не требуется.

### 3.2. Возможности гостя

Гость может пользоваться приложением без регистрации.

Основной сценарий:

1. Открыть главную страницу приложения.
2. Перейти к записи на звонок.
3. Посмотреть каталог доступных типов встреч.
4. Выбрать подходящий тип встречи.
5. Открыть календарь доступных дат на ближайшие 14 календарных дней.
6. Выбрать свободную дату.
7. Выбрать доступное время.
8. Подтвердить бронирование.
9. Увидеть результат успешной записи.

Длительность бронирования определяется выбранным типом встречи.

## 4. Правила работы календаря

### 4.1. Доступные даты

- Окно записи охватывает 14 календарных дней.
- Окно автоматически сдвигается с течением времени.
- Начало окна может приходиться на сегодняшний или завтрашний день.
- Конкретный вариант начала окна необходимо выбрать и зафиксировать в спецификации.
- Рабочие часы владельца и часовой пояс также необходимо определить и записать в спецификации.

### 4.2. Доступные временные интервалы

- Длительность встречи определяется типом встречи.
- Шаг доступных стартов встреч необходимо определить и зафиксировать в спецификации.
- Время должно соответствовать рабочим часам владельца.
- Система должна учитывать уже существующие бронирования.

### 4.3. Запрет пересечения бронирований

Одно и то же время нельзя забронировать дважды.

Запрещены:
- Полное совпадение интервалов.
- Частичное пересечение интервалов.
- Пересечение встреч разных типов.

Следующая встреча может начинаться точно в момент окончания предыдущей.

Правила должны соблюдаться даже при одновременном поступлении двух запросов на бронирование одного или пересекающегося времени.

Проверка конфликтов должна выполняться на стороне сервера, а не только в интерфейсе.

### 5.3. Приоритет источников

Важно различать обязательные требования и визуальные примеры.

1. Письменное техническое задание определяет обязательную функциональность и бизнес-правила.
2. Скриншоты демонстрации используются для понимания интерфейса и пользовательского пути.
3. Если поведение демонстрации противоречит письменному заданию, приоритет имеет письменное задание.

Например, демонстрация показывает слоты по 30 минут и рабочее время с 09:00 до 18:00. Это не означает, что в нашем приложении все встречи должны длиться 30 минут. По основному заданию длительность зависит от выбранного типа встречи.

Демонстрационные даты и количество свободных слотов также не являются фиксированными требованиями.

В демонстрации показаны интервалы с шагом 30 минут, начиная с 09:00.

**Предположения:**
- Прошедшие даты недоступны для выбора.

**Что видно на изображении:**

## 6. Технические требования

### 6.1. Технологический стек

Технологический стек выбирается самостоятельно.

Перед выбором необходимо проверить наличие генератора клиентского SDK из OpenAPI для выбранного языка frontend.

### 6.2. API и генерация типов

Обязательные требования:

- API описывается с помощью TypeSpec.
- На основе TypeSpec генерируется OpenAPI-спецификация.
- Для frontend генерируется клиентский SDK из OpenAPI.
- Если выбранный backend-фреймворк поддерживает генерацию серверных типов и маршрутов, необходимо использовать эту возможность.
- Если серверная генерация недоступна, backend реализуется по контракту и проверяется тестами.

### 6.3. Docker

Приложение должно:

- Собираться в Docker-образ.
- Запускаться внутри Docker-контейнера.
- Иметь понятную инструкцию запуска в README.md.

### 6.4. Хранение данных

Допускаются два варианта:

1. Хранение данных в памяти процесса.
2. Использование базы данных с сохранением данных.

Если используется память процесса, после перезапуска приложения бронирования сбрасываются. Это ограничение обязательно нужно описать в README.md.

Сохранение данных после перезапуска не является обязательным условием приёмки.

## 7. Требования к качеству

Приложение должно:

- Корректно отображать доступные даты и временные интервалы.
- Не позволять бронировать занятые интервалы.
- Корректно обрабатывать пересечения встреч.
- Проверять конфликты при одновременных запросах.
- Показывать пользователю результат бронирования.
- Обновлять доступность времени после успешной записи.

Критически важные бизнес-правила должны проверяться автоматическими тестами.

## 10. Итоговый результат

В результате должен получиться небольшой, но законченный сервис бронирования звонков.

Владелец создаёт типы встреч и просматривает записи. Гость выбирает тип встречи, дату и свободное время, после чего подтверждает бронирование.

Сервис предотвращает пересечение встреч, корректно обрабатывает одновременные запросы, использует TypeSpec, OpenAPI и сгенерированный клиентский SDK, собирается в Docker и может быть опубликован в облаке.

Главная цель проекта — не просто получить работающий интерфейс, а пройти полный цикл разработки реального приложения с помощью ИИ-агентов.
