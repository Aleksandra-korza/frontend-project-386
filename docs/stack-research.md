| Требование | Что оно значит для стека |

## 3. Общие для всех вариантов части

### 3.1. TypeSpec и OpenAPI

- TypeSpec 1.0 вышел в GA; эмиттер `@typespec/openapi3` стабилен и генерирует OpenAPI 3.0 или 3.1 (настраивается). Это одинаково для всех вариантов.
- Выбор версии OpenAPI влияет на совместимость генераторов: часть серверных инструментов полноценно работает только с 3.0 (см. варианты B и A). Генерация в 3.0 снимает этот риск.

### 3.2. Frontend

Во всех вариантах frontend — **TypeScript + Vite + React** (React можно заменить на Vue без влияния на остальное исследование). Причины:

- для TypeScript есть несколько зрелых генераторов клиента из OpenAPI;
- проект — часть программы «Фронтенд-разработчик» Hexlet;
- интерфейс небольшой: главная, каталог, мастер бронирования, `/admin`.

Генераторы SDK для TypeScript:

| Инструмент | Что генерирует | Плюсы | Минусы |
|---|---|---|---|
| `openapi-typescript` + `openapi-fetch` | Только типы; запросы через тонкую типизированную обёртку над `fetch` | Минимум сгенерированного кода, быстрый, почти нет runtime | Вызовы вида `client.POST("/bookings", …)`, а не отдельные функции |
| `@hey-api/openapi-ts` | Типы + SDK-функции на каждую операцию + клиент; опционально Zod-схемы и плагины | Похоже на «настоящий SDK», удобно для TanStack Query | Больше сгенерированного кода, версии до 1.0 — API генератора меняется |
| `@typespec/http-client-js` | Клиент напрямую из TypeSpec | Без промежуточного OpenAPI | Preview-статус; ТЗ требует именно SDK **из OpenAPI** (TC-05) — не подходит |

Оба первых инструмента удовлетворяют TC-05.

## 4. Варианты стека

### Вариант A. TypeScript целиком: React + Fastify (Node.js)

| Слой | Технология |
|---|---|
| Frontend | TypeScript, Vite, React |
| SDK | `@hey-api/openapi-ts` или `openapi-typescript` + `openapi-fetch` |
| Backend | Node.js, Fastify |
| Серверные типы | `openapi-typescript` из того же OpenAPI |
| Серверные маршруты и валидация | `fastify-openapi-glue`: регистрирует маршруты и JSON-схемы валидации по OpenAPI, обработчики сопоставляются по `operationId` |
| Тесты | Vitest; HTTP-тесты через `fastify.inject()` без поднятия порта |
| Docker | Один образ: сборка frontend → статика раздаётся Fastify |

**Генерация серверного кода (TC-06).** Маршруты и валидация запросов строятся из OpenAPI во время запуска, типы — генерируются. Это contract-first, но через сторонний плагин, а не через сам Fastify. Альтернатива — `@typespec/http-server-js` (генерирует роутер прямо из TypeSpec), но он в alpha/dev-версиях 0.58, поэтому для учебного проекта рискован.
Ограничение: Fastify по умолчанию валидирует JSON Schema draft-07; для конструкций OpenAPI 3.1 нужна дополнительная настройка. Решение — генерировать OpenAPI 3.0.

**Реализация требований:**
- *Атомарность (BR-18).* Node.js выполняет JavaScript в одном потоке. Если «проверить пересечения и вставить бронь» — синхронный код без `await` между шагами, два запроса физически не могут выполниться одновременно. Простейший вариант из трёх.
- *Часовой пояс (BR-03).* Нужна библиотека с поддержкой IANA-поясов (Luxon, date-fns-tz) или `Temporal`, если он доступен в выбранной версии Node.js — проверить.
- *Общий код.* Функции расчёта слотов можно при желании переиспользовать на frontend, но источник истины — сервер (BR-19).
- *Тесты конкурентности (NFR-02).* `Promise.all` из двух `inject()` — короткий и наглядный тест.

**Плюсы:** один язык и один пакетный менеджер на весь проект; TypeSpec и генераторы — тоже npm; минимум инфраструктуры; самый простой Docker-образ и CI.
**Минусы:** серверная генерация через сторонний плагин; сгенерированные типы нужно вручную связать с обработчиками; качество типизации обработчиков ниже, чем у варианта B.

### Вариант B. React + Go (`oapi-codegen`)

| Слой | Технология |
|---|---|
| Frontend | TypeScript, Vite, React |
| SDK | как в варианте A |
| Backend | Go, `net/http` или chi |
| Серверные типы и маршруты | `oapi-codegen` в режиме `strict-server`: генерирует модели, интерфейс сервера с методом на каждую операцию, разбор запросов и кодирование ответов |
| Тесты | стандартный `testing`, `httptest` |
| Docker | Multi-stage: Node.js (TypeSpec, сборка frontend) → Go (сборка бинарника) → минимальный runtime-образ |

**Генерация серверного кода (TC-06).** Самая полная из трёх вариантов: компилятор Go не даст собрать сервер, пока не реализованы все операции контракта. `oapi-codegen` зрелый; поддержка OpenAPI 3.1 появилась только в v2.8.0 как «начальная», поэтому надёжнее генерировать 3.0.

**Реализация требований:**
- *Атомарность (BR-18).* HTTP-запросы обрабатываются параллельными горутинами — обязательно `sync.Mutex` вокруг «проверить и вставить». Несложно, но ошибку легко допустить; нужен тест с `-race`.
- *Часовой пояс.* `time.LoadLocation("Europe/Warsaw")` из стандартной библиотеки; в минимальном образе нужен `time/tzdata` или пакет tzdata.
- *Тесты.* Встроены в язык, быстрые.

**Плюсы:** строгая генерация сервера из контракта; маленький быстрый образ; сильная стандартная библиотека для времени и HTTP.
**Минусы:** два языка и два набора инструментов; Node.js всё равно нужен для TypeSpec и frontend; выше порог входа для frontend-разработчика; сложнее Dockerfile.

### Вариант C. React + C# ASP.NET Core (`@typespec/http-server-csharp`)

| Слой | Технология |
|---|---|
| Frontend | TypeScript, Vite, React |
| SDK | как в варианте A |
| Backend | .NET (ASP.NET Core) |
| Серверные типы и маршруты | `@typespec/http-server-csharp` генерирует контроллеры и модели прямо из TypeSpec; бизнес-логика подключается через DI |
| Тесты | xUnit, `WebApplicationFactory` |
| Docker | Multi-stage: Node.js → .NET SDK → ASP.NET runtime |

**Генерация серверного кода (TC-06).** Единственный вариант, где сервер генерируется из того же TypeSpec, что и OpenAPI. Однако эмиттер в alpha (0.58.x); есть открытые issues (неверные `[Route]` у базовых контроллеров, ошибка загрузки эмиттера в одной из alpha), идёт переписывание на новый emitter framework. Сгенерированный проект рассчитан на .NET 9, поддержка которого заканчивается 10.11.2026 — уже требуется переход на .NET 10.

**Реализация требований:**
- *Атомарность.* Многопоточность — нужна блокировка (`lock`).
- *Часовой пояс.* `TimeZoneInfo` с IANA-идентификаторами (на Linux работает из коробки) или NodaTime.

**Плюсы:** генерация сервера прямо из TypeSpec; зрелая платформа.
**Минусы:** нестабильный эмиттер; самый тяжёлый образ и тулчейн; три экосистемы (Node.js, .NET, frontend); избыточно для небольшого проекта.

### Рассмотрены и отклонены

| Вариант | Причина |
|---|---|
| Python + FastAPI | FastAPI — code-first (OpenAPI строится из кода). Contract-first через `fastapi-code-generator` возможен, но примеры и подтверждённая поддержка — OpenAPI 3.0; добавляет третий язык без явных преимуществ |
| Next.js / полнофункциональные мета-фреймворки | Смешивают frontend и backend; контракт TypeSpec → OpenAPI → SDK становится избыточным при server actions; не дают генерации маршрутов |
| `@typespec/http-server-js` как основной backend | alpha/dev-версии, API меняется |

## 5. Сравнение

Оценка: ●●● — хорошо, ●● — приемлемо, ● — слабо.

| Критерий | A. TS + Fastify | B. Go + oapi-codegen | C. C# + TypeSpec emitter |
|---|---|---|---|
| SDK для frontend из OpenAPI (TC-05) | ●●● | ●●● | ●●● |
| TypeSpec → OpenAPI (TC-03, TC-04) | ●●● | ●●● | ●●● |
| Генерация серверных типов и маршрутов (TC-06) | ●● плагин + типы | ●●● strict-server | ●● из TypeSpec, но alpha |
| Стабильность инструментов генерации | ●● | ●●● | ● |
| Атомарное бронирование в памяти (BR-18) | ●●● однопоточный event loop | ●● mutex | ●● lock |
| Часовой пояс и календарная логика | ●● нужна библиотека | ●●● стандартная библиотека | ●●● |
| Тестирование (NFR-01, NFR-02) | ●●● Vitest + inject | ●●● testing + httptest | ●●● xUnit |
| Docker (TC-09, TC-10) | ●●● один runtime | ●●● маленький образ, сложнее сборка | ●● тяжёлый образ |
| Количество языков и тулчейнов | ●●● один | ●● два | ● три экосистемы |
| Сложность для небольшого проекта | ●●● низкая | ●● средняя | ● высокая |
| Удобство работы ИИ-агента и дальнейшей разработки | ●●● | ●●● | ●● |

## 6. Рекомендация

**Рекомендуемый стек — вариант A: TypeScript целиком.**

| Слой | Выбор |
|---|---|
| Контракт | TypeSpec → OpenAPI 3.0 (`@typespec/openapi3`) |
| Frontend | TypeScript, Vite, React |
| SDK | генератор из OpenAPI для TypeScript (конкретный — решение T-02) |
| Backend | Node.js + Fastify |
| Серверная генерация | типы через `openapi-typescript`, маршруты и валидация через `fastify-openapi-glue` |
| Хранилище | Map/массивы в памяти процесса |
| Тесты | Vitest (unit + HTTP через `inject`) |
| Docker | один multi-stage образ, Fastify раздаёт собранный frontend |

**Почему, применительно к требованиям:**
1. **BR-18 / AC-18** — самое рискованное требование. В Node.js атомарность «проверить и вставить» в памяти обеспечивается синхронным кодом без блокировок; в B и C нужна ручная синхронизация.
2. **TC-03…TC-05** — TypeSpec, OpenAPI и генератор SDK уже живут в npm; вариант A не добавляет второй экосистемы.
3. **TC-06** выполняется: маршруты, валидация и типы берутся из контракта; отклонения от контракта ловятся валидацией и HTTP-тестами (запасной путь ТЗ §6.2).
4. **TC-09…TC-11** — один процесс, один образ, хранение в памяти без внешних сервисов.
5. Один язык упрощает работу ИИ-агентов, тикеты и ревью для frontend-разработчика.

**Преимущества:** минимальная сложность; один язык; простая атомарность; быстрые тесты; простой Docker.

**Недостатки и риски:**
- серверная генерация слабее, чем в варианте B: обработчики не обязаны реализовать все операции на уровне компилятора — компенсируется тестами на каждую операцию;
- зависимость от стороннего плагина `fastify-openapi-glue`;
- в JavaScript нет встроенной зрелой работы с часовыми поясами (до `Temporal`) — нужна библиотека и тесты на смену летнего времени;
- генераторы SDK в версиях 0.x/7.x — фиксировать версии.

**Когда выбрать вариант B:** если строгая генерация сервера (TC-06) важнее простоты и разработчик готов работать с Go.
