## 1. Описание приложения

«Календарь звонков» — упрощённый сервис бронирования времени для встреч по мотивам Cal.com [ТЗ §2].

Владелец календаря создаёт типы встреч и просматривает записи. Гость без регистрации выбирает тип встречи, дату и свободное время, после чего подтверждает бронирование [ТЗ §10]. Сервис предотвращает пересечение встреч, в том числе при одновременных запросах [ТЗ §4.3, §10].

### 1.1. Входит в объём

- Создание типов встреч и просмотр предстоящих записей владельцем [ТЗ §3.1].
- Каталог типов встреч, календарь доступных дат, выбор времени и бронирование гостем [ТЗ §3.2].
- Серверная проверка конфликтов бронирований [ТЗ §4.3].
- API на TypeSpec, OpenAPI, сгенерированный клиентский SDK [ТЗ §6.2].
- Сборка и запуск в Docker [ТЗ §6.3].

## 3. Пользовательские сценарии

### UC-01. Владелец создаёт тип встречи [ТЗ §3.1]

1. Владелец открывает `/admin`.
2. Вводит название, описание и длительность (правила полей — BR-06, BR-07).
3. Сохраняет тип; при ошибке валидации видит сообщение.
4. Тип появляется в каталоге гостя.

### UC-02. Владелец просматривает предстоящие записи [ТЗ §3.1]

1. Владелец открывает раздел записей в `/admin`.
2. Видит будущие записи всех типов встреч (BR-24).

### UC-03. Гость бронирует встречу [ТЗ §3.2]

1. Открывает главную страницу.
2. Переходит к записи на звонок.
3. Просматривает каталог типов встреч и выбирает тип.
4. Открывает календарь доступных дат (BR-01…BR-04) с подписью часового пояса.
5. Выбирает дату.
6. Выбирает доступное время.
7. Вводит имя и email и подтверждает бронирование.
8. Видит результат успешной записи.

### UC-04. Конфликт при бронировании [ТЗ §4.3, §5.2]

1. Гость выбрал время и заполняет форму.
2. Тем временем это или пересекающееся время бронирует другой гость.
3. Гость подтверждает бронь — сервер отклоняет запрос из-за конфликта.
4. Гость видит понятное сообщение; список свободных слотов обновляется [D-09].
5. Гость выбирает другое время.

### UC-05. Повторное бронирование [ТЗ §5.1], [Демо]

1. После успешной брони гость нажимает кнопку создания новой записи.
2. Начинается новый процесс бронирования; тот же email можно использовать повторно (BR-22).

### 9.4. Следствия решений

**Шаг 30 минут, длительность кратна 15 минутам, запрет пересечений (D-04 + D-14 + BR-14…BR-17).**

- Если длительность не кратна 30 минутам (15, 45, 75 … мин), встреча заканчивается между точками сетки. Следующая встреча может начаться только в ближайшей точке сетки, поэтому остаётся неиспользуемый промежуток 15 минут. Пример: бронь 09:00–09:45 → ближайший возможный старт 10:00, промежуток 09:45–10:00 не используется.
- Такая бронь блокирует все старты, интервалы которых с ней пересекаются. Пример: бронь 09:00–09:45 блокирует старт 09:30 для любого типа, так как `09:30 < 09:45`.
- Правило «встреча вплотную к предыдущей» (BR-17) на практике применимо только к броням, окончание которых совпадает с точкой сетки, то есть длительность которых кратна 30 минутам.
- Тип на 15 минут занимает старт 30-минутной сетки так же, как тип на 30 минут: счётчик для них одинаков (18 стартов в свободный день).

**Скрытие списка записей не защищает его (D-05 + D-11).** Список убран из гостевой навигации, но `/admin` по-прежнему открыт любому (SEC-01).

**Расхождение с демо (D-11).** В демо пункт «Предстоящие события» есть в общей навигации; приоритет у решения разработчика.
